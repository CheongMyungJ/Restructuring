# Restructuring — rekit: 레거시 코드 → AI 재개발 키트 생성기

**rekit**은 레거시 코드와 각종 자료(설계서·인터페이스 정의서·PDF·엑셀·워드·HWP 등)를 입력받아, AI가 그 시스템을
**새 기술 스택으로 재개발할 수 있게 하는 데이터("재개발 키트")** 를 만들어 주는 도구입니다.
코드만으로는 알 수 없는 것(운영 설정 값, 의도된 특이동작, 문서-코드 불일치, 누락 자료 등)은 **사람에게 질문하거나
자료를 요청**하고, 답을 키트에 반영하면서 끝까지 완료합니다.

- 실행 환경: **Claude Code**(`claude` CLI, 로그인 상태) + Python 3.9+ (외부 패키지 불필요. 문서 변환 패키지가 있으면 활용)
- 대상: 언어·프레임워크 무관(범용). **SSD/임베디드 펌웨어(C/C++)**, **Java/Spring 데이터 처리·배치**는 정밀 체크리스트 내장
- 산출물: **레거시 구조와 분리된** 한국어 명세(식별자·포맷·SQL·메시지는 원문 그대로) + 레거시를 실제 실행해 얻은 골든 테스트
  + 레거시 코드를 보지 않고 만든 **목표 설계** + 그 설계 순서의 구현 계획 + 참고용 레거시 분석. 동작은 그대로 지키되
  레거시 코드 구조를 따라가지 않는 **재설계**를 목표로 합니다(§4, §8).

> 도구의 형태와 데이터 형식은 **자체 실험으로 결정**했습니다(실제·합성 레거시 4종, AI 재개발 수십 회를 숨김 테스트로 채점,
> 실제 SSD 펌웨어 재구현자 시험 70문항). 요약은 아래 §8, 상세는 [`experiments/REPORT.md`](experiments/REPORT.md)와
> 구조 독립성 실험 [`experiments/REPORT_STRUCTURE.md`](experiments/REPORT_STRUCTURE.md).

## 1. 설치

**Claude Code 플러그인 (권장)** — Claude Code 안에서:
```
/plugin marketplace add CheongMyungJ/Restructuring
/plugin install rekit@restructuring
```
(Claude Code 2.1.275+ 는 한 줄: `/plugin install rekit --marketplace CheongMyungJ/Restructuring`)

**터미널 도구로만** 쓰려면:
```
git clone https://github.com/CheongMyungJ/Restructuring
python3 Restructuring/plugins/rekit/engine/rekit.py doctor     # 필수/선택 도구 점검
```

## 2. 사용법 — Claude Code에서 대화로
```
/rekit:start ./legacy-src ./docs
```
1. **환경 점검** → **사전 인터뷰**: 재개발 목적, **목표 스택**, **새 구조에 대한 요구**(목표 설계의 입력 — 목표 스택을
   비워 두면 설계가 엉뚱한 스택을 고를 수 있음), 반드시 유지할 호환성, 제외 범위, 실행 환경,
   **운영에서만 적용되는 설정 값/파일**(JVM 옵션, 릴리스 빌드 플래그 등 — 실험상 결과를 가장 크게 좌우), 답변자.
2. **규모·비용 안내** 후 품질 프리셋(`max`/`balanced`/`economy`)과 비용 상한을 정하고 시작합니다.
3. 엔진이 **백그라운드**로 분석합니다. 다른 일을 해도 되고 `/rekit:status`로 확인합니다.
4. 사람의 확인이 필요하면 **선택지 형태의 질문**을 보여 줍니다(`/rekit:answer`). 자료 요청이면 파일 경로를 받습니다.
   다른 담당자에게 물어야 하면 **질문지(Markdown)로 내보내고** 작성본을 다시 가져올 수 있습니다.
5. 완료되면 키트 위치·목표 설계 요약·소스 커버리지·구조 누출 검사 결과·남은 질문(적용된 가정)·비용을 보고합니다.

## 3. 사용법 — 터미널에서
```
RK="python3 plugins/rekit/engine/rekit.py"
$RK init  work/mysys --code ./legacy-src --materials ./docs --preset balanced --budget 100
$RK run   work/mysys --bg          # 백그라운드 실행 (로그: work/mysys/.rekit/run.log)
$RK wait  work/mysys               # 멈출 때까지 대기 → done / waiting_human / failed / paused
$RK answer work/mysys              # 대화형 답변 (번호·자유입력, s=보류, f <경로>=자료로 답변)
$RK run   work/mysys --bg          # 이어서 진행 (끝난 단계는 건너뜀)
$RK status work/mysys
```
- 질문지로 받기: `$RK questions work/mysys --export 질문지.md` → 담당자 작성(답변: 줄, 번호/자유입력/파일 경로/모름) →
  `$RK answer work/mysys --import 질문지.md`
- 개별 답변: `$RK answer work/mysys --set Q-XXX-01 "답" [--file 자료경로]`, 보류: `--defer Q-XXX-01`
- 자료 추가: `$RK add-material work/mysys ./추가자료.pdf` · 소스 커버리지: `$RK coverage work/mysys`
- 종료코드: 0 완료/정상, **10 사람 확인 필요**, 1 오류(그대로 다시 실행하면 이어서 진행)

## 4. 키트(산출물) 구조 — 세 층
키트는 **무엇을 지켜야 하는가(명세)**, **새로 어떻게 만들 것인가(목표 설계)**, **레거시는 어떻게 했는가(참고)** 를
분리합니다. 구현 AI가 레거시의 모듈 구조·함수 분해·내부 이름을 그대로 넘겨받아 사실상 이식(port)하게 되는 것을 막고,
동작은 그대로 유지한 채 **재설계**할 수 있게 하기 위해서입니다(§8 실험).
```
kit/
  README.md            구현 AI의 진입점: 세 층과 읽는 규칙, 유지 필수 계약 목록, 테스트·계획 사용법
  ── 명세(spec): 레거시 구조와 무관한 '무엇' ─────────────────────────────────────────────
  00_overview.md       목적·범위·시스템 경계·외부 주체·기능 목록(CAP-*)·종단 흐름(FL-*)
  01_glossary.md       도메인 용어 ↔ 의미 (계약 식별자만 원문)
  02_constraints.md    외부가 강제하는 제약: 호출/실행 모델, 운영 설정 값(운영값!), 빌드 변형, 호환 요구
  03_interfaces/       외부 계약(IF-*): API/ABI, 파일·전문 포맷(바이트 단위), DB·SQL 의미, 명령/프로토콜, 운영 인터페이스
  04_data/             영속·공유 데이터 계약(DM-*): 온미디어(NAND) 포맷, 파일, 테이블, 불변식
  05_behavior/CAP-*.md 기능별 동작: 규칙 BR(조건→관측 결과), 불변식 INV, 상태 SM, 오류 ERR, 결과 결정 알고리즘 ALG
  06_nfr.md            성능·메모리·타이밍·신뢰성·운영 요구
  07_tests/            기능별 테스트 벡터(TV-*) + 레거시를 실제 실행해 얻은 골든(특성화) 테스트와 실행 스크립트
  08_decisions.md      사람이 확인한 사실·결정(DEC-*): 운영 설정, 유지할 특이동작, 폐기 대상
  09_open_questions.md 미해결 질문과 현재 적용한 가정(사람이 검토할 위험 목록)
  ── 목표 설계(design/): 레거시 코드를 보지 않고 명세만으로 작성(클린룸) ─────────────────
  design/architecture.md  구성요소(C-*)·책임·의존 규칙·실행 모델·데이터 소유·계약 경계·소스 배치안
  design/decisions.md     ADR-*: 대안·선택·이유, 레거시 구조 문제(LP-*)를 어떻게 피하는가
  design/allocation.md    모든 명세 ID → 담당 구성요소 할당표
  10_plan.md           목표 설계 구성요소 순서의 구현 태스크(T-*), 태스크별 컨텍스트 팩(명세 ID + 설계 절), 완료 기준
  ── 레거시 참고(legacy_ref/): '어떻게' — 모호점 확인용, 구조 템플릿 아님 ──────────────────
  legacy_ref/structure.md         레거시 모듈·실행 모델·의존 관계, 모듈→기능 매핑, 제외/미사용 코드
  legacy_ref/structure_issues.md  새 시스템에 가져가면 안 되는 레거시 구조 문제(LP-*)
  legacy_ref/modules/<모듈>.md     내부 알고리즘(레거시에 충실한 의사코드)·내부 자료구조·상수·식별자, 커버리지 표
  trace.json           ID → 키트 파일·레거시 소스 위치·신뢰도
```
- 명세에는 레거시 내부 함수·변수·타입·파일 이름과 소스 경로를 쓰지 않습니다(계약 식별자는 원문 유지). 출처는 `trace.json`에만.
- 알고리즘은 **관측 결과를 결정할 때만** 명세에 두고(선택 기준·동률 처리·공식·상수 + `결과 결정: …`), 레거시 제어 흐름을
  옮긴 의사코드는 `legacy_ref/`에 둡니다.
- 신뢰도 `[코드확인]` `[실행확인]` `[문서]` `[사람확인]` `[추정]`, 사람이 바꿔도 된다고 한 항목은 `[변경 허용: DEC-…]`.

## 5. 동작 방식
```
inventory → survey → units(병렬) → synthesize → specify(기능별 병렬) → gate1(사람) → characterize
          → [review/fix] → gate2(사람) → neutralize → design(클린룸) → finalize
```
| 단계 | 내용 |
|---|---|
| inventory | 파일 분류·LOC·토큰·심볼 수집(결정적), 자료 텍스트 변환(PDF/DOCX/XLSX/PPTX/HWPX, HWP·DOC 등은 변환기 있으면) |
| survey | 시스템 경계·외부 계약·**기능(CAP) 목록**(외부 관점) 파악, 분석용 **모듈 단위 분할**(작을수록 정밀 — 실측), 초기 질문 |
| units | 단위별 독립 AI 세션이 코드를 **한 줄도 빠짐없이** 읽고 두 관점으로 기록: 레거시 '어떻게'(`legacy_ref/modules/`, 의사코드·커버리지 표·구조 문제)와 기능별로 묶은 관측 가능한 '무엇'(노트) |
| synthesize | 인터페이스·데이터·개요·흐름·제약 통합, 기능 목록 확정, 구조 문제 LP-* 정리, 질문 중복 제거·우선순위화 (대규모는 서브시스템별 계층 통합) |
| specify | **기능별** 세션이 여러 모듈의 노트를 합쳐 구조 중립 명세(`05_behavior/CAP-*.md`)와 테스트 벡터 작성(모호하면 코드 확인) |
| gate | 사람에게 질문(blocking/important) → 답을 키트에 반영(DEC-*), 후속 질문 |
| characterize | 레거시를 (시뮬레이터·스텁·임베디드 DB 등으로) 실제 빌드·실행해 **골든 테스트** 생성, 키트 교정 |
| review/fix (`max`만) | **코드 없이 명세만 가진 구현자 AI**가 빠짐·모호함을 찾고, 코드를 보는 AI가 메우거나 질문으로 전환 |
| neutralize | 명세에 남은 레거시 내부 이름·파일명·소스 경로를 **결정적으로 검출**하고, AI가 관측 용어로 다시 쓰거나 legacy_ref로 이동 |
| design | **레거시 코드 접근 없이** 명세·사전 인터뷰(목표 스택·구조 요구)·구조 문제 목록만으로 목표 아키텍처·ADR·할당표 작성 |
| finalize | 소스 커버리지 점검, 목표 설계 기준 구현 계획·README·추적표 완성, 최종 구조 누출 측정 |

각 AI 단계는 새 `claude -p` 세션이며, 상태는 작업폴더 `.rekit/`에 저장되어 **중단 후 재개**할 수 있습니다.
구조 누출 측정 결과는 `.rekit/neutrality.json`(단계별 before/after/final)에 남습니다.

## 6. 키트로 재개발하기
새 프로젝트 저장소에 `kit/`를 복사하고 Claude Code에서
```
/rekit:implement kit [레거시 코드 경로]
```
또는 "kit/README.md를 읽고 10_plan.md 순서대로 구현해줘". 구현 AI는 **구조는 `design/`**, **동작은 명세**를 따르고,
태스크별 컨텍스트 팩만 읽으며 테스트 벡터와 골든 테스트로 스스로 검증합니다. 레거시 코드(또는 `legacy_ref/`)는 특정 명세
ID가 모호할 때 `trace.json`으로 그 위치만 확인하는 데 씁니다.

재개발 결과가 레거시 구조를 얼마나 닮았는지는 결정적으로 측정할 수 있습니다:
```
python3 plugins/rekit/engine/rekit.py similarity <레거시 코드> <신규 코드> --contract 'fw_api.h' --contract 'hal/*.h'
```
| 지표 | 의미 |
|---|---|
| M1 파일 대응률 | 레거시 소스 파일이 신규 코드에 다시 나타난 비율(같은 파일명, 또는 그 파일 함수의 절반 이상이 한 신규 파일로 대응) |
| M2 내부 이름 재사용 | 레거시 내부 정의 이름(함수·타입·클래스·매크로)을 신규 코드가 다시 정의한 비율(계약 식별자 제외) |
| M3 구조 클론률 | 식별자·리터럴을 지운 토큰 20-gram 중 레거시와 같은 비율(이름만 바꾼 이식 탐지). 원문 그대로 비율도 함께 표시 |
| M4 함수 대응률 | 레거시의 비자명 함수 중 경계와 본문 형태가 거의 같은(정규화 5-gram Jaccard ≥ 0.5) 신규 함수가 있는 비율 |
| **LSS** | 레거시 구조 유사도 = 100 × 평균(M1~M4). 레거시 자기 자신 = 100, 독립 설계일수록 낮음 |
`--contract`로 지정한 계약 파일(그대로 유지해야 하는 헤더 등)은 양쪽에서 제외되고 그 식별자는 재사용으로 세지 않습니다.

## 7. 프리셋·비용
| 프리셋 | 모델 | 분석 단위 | 단계 | 용도 |
|---|---|---|---|---|
| `max` | Opus | 작게(≈10K 토큰) | 특성화 + 검토/보완 | 정밀도 최우선 (비용 최대) |
| `balanced` (기본) | Opus | 중간(≈20K 토큰) | 특성화 | 일반 권장 |
| `economy` | Sonnet | 크게(≈40K 토큰) | 특성화 | 대형 코드베이스 1차 분석, 비용 절감 |

검토/보완(review/fix: 코드 없이 키트만 가진 AI가 빈틈을 찾고 메움)은 실측에서 통합 직후 대비 정답률을 올리지 못하고
(95.1% → 94.1%) 비용만 약 2.4배가 되어 `max`에서만 켭니다. 레거시를 실제 실행하는 특성화(골든 테스트)는 모든 프리셋에서 켭니다.
비용은 코드 규모·단위 수에 비례합니다. 실측(Opus, 사람 질의응답 포함 전체 파이프라인):

| 레거시 | 코드 토큰 | 전체(검토/보완 포함) | 검토/보완 제외(≈`balanced`) |
|---|---|---|---|
| Java/Spring 배치 3.2K LOC | 37K | $35~71 | $25~44 (세 층 키트: 약 $84) |
| SSD 펌웨어(합성) 4.5K LOC | 42K | $109~167 | $57~85 (세 층 키트: 약 $125) |
| SSD 펌웨어(Cosmos+) 7.4K LOC | 81K | $107 | $61 |

세 층 키트(현재 형식)는 기능별 명세·계약 경계 점검·클린룸 설계 단계가 더해져 이전 형식보다 약 1.5~1.8배입니다
(실측: S3 $46 → 약 $84, S4 $82 → 약 $125; 증가분 대부분이 기능별 명세 단계).
대략 코드 1만 토큰당 `balanced` $15~30, `max` $25~45, `economy`(Sonnet) 그 1/5 수준. 레거시 실행(특성화)이 길어지는
펌웨어가 더 비쌉니다. `--budget`으로 상한을 두면 도달 시 멈추고 재개할 수 있습니다.

## 8. 실험으로 확인한 사실 (요약)
| 샘플 (숨김 평가) | 코드만 | 서술형 문서 | 키트(사람 없음) | **키트 + 사람 질의응답** |
|---|---|---|---|---|
| S1 NAND FTL C (89 체크) | 100% | 100% | 100% | – |
| S2 실제 SSD 펌웨어 (70문항 시험) | 87% | 88% | **95%** (단일 세션 키트 93%) | – (실행 불가 샘플) |
| S3 Spring 배치 (145 체크) | 134 | 134 | 134 | **145 / 145** (6회 + 실사용 흐름 2회) |
| S4 SSD 펌웨어 (178 체크) | 161, 132 | 132 | 132 | **178 / 178** (6회) |

- 코드에 **들어 있는** 동작은 강한 AI가 코드·문서·키트 어느 것으로도 거의 완벽히 재현한다. 남은 실패는 전부 **코드 밖 지식**
  (운영 JVM 옵션, 릴리스 빌드 플래그)이었고, 키트가 그 질문을 스스로 찾아 사람에게 물었을 때만 해결됐다.
- 잘 만든 키트는 원본 코드보다 정확하게 답하게 한다(S2 95% vs 87%, 오답·환각 0~1). 분석 단위가 작을수록 정밀(95% vs 91%).
- 재개발 비용은 데이터에 따라 다르다: 서술형 문서는 코드 대비 약 절반(S3), 키트+코드는 레거시를 이식하고 결정만 반영해
  가장 빨랐다(S4 7분·$2). 키트만 주면 명세를 모두 구현하느라 코드 기반보다 오래 걸린 경우도 있다(S3 14~40분 vs 24~30분).
- 검토/보완 단계는 정확도 이득 없이 비용 2.4배 → `max`에만. 상세 수치·방법·한계: [`experiments/REPORT.md`](experiments/REPORT.md)
