# 실험 보고서 — AI 재개발용 데이터의 형태와 생성 도구의 형태 결정

> 작성 중(실험 진행에 따라 갱신). 원자료: `experiments/results/`

## 1. 실험 질문
| ID | 질문 |
|---|---|
| Q1 | AI가 레거시를 재개발하기에 **가장 효율적이고 충분한 데이터 형태**는 무엇인가? (코드 그대로 / 서술형 문서 / 구조화 명세 / 명세+골든테스트 / 명세+코드) |
| Q2 | 그 데이터를 만드는 **도구의 형태**: 단일 AI 세션(Form X) vs 결정적 오케스트레이션 파이프라인(Form Y) |
| Q3 | 코드만으로 알 수 없는 지식(운영 설정, 의도된 특이동작 등)을 **사람에게 묻는 루프**가 재개발 결과를 개선하는가? |

## 2. 실험 대상(샘플)
| ID | 종류 | 규모 | 실행/평가 방식 | 특징 |
|---|---|---|---|---|
| S1 | 실제 NAND 플래시 변환 계층(FTL) C 라이브러리(오픈소스 dhara를 비식별화) | C 3.2K LOC | 숨김 블랙박스 테스트 89개: 공개 API, 용량 계산, 전원 차단 33지점 트레이스, **온플래시 포맷 상호호환(구↔신)** | 작고 깔끔함, 모델이 원본을 학습했을 가능성 |
| S2 | 실제 NVMe SSD 펌웨어(Cosmos+ OpenSSD GreedyFTL 3.0) + PDF 자료 2종(198쪽) | C 8.8K LOC | 하드웨어 의존(실행 불가) → **재구현자 관점 시험 70문항(248 핵심사항)**, 코드 근거 정답 | 실제 펌웨어의 놀라운 동작(미기록 LBA 읽기 시 stale 데이터, FLUSH 무동작 등) 포함 |

| S4 | 합성 레거시 SSD 컨트롤러 펌웨어(NVMe 유사 명령, 쓰기 캐시, FTL, GC/WL, 배드블록, 리드리트라이, SMART, 전원断 복구) | C 수천 LOC | 숨김 테스트(명령 의미·SMART 값·온NAND 호환·전원断 등) | **릴리스 빌드 플래그**(운영 전용), 유지해야 할 버그성 동작, 미공개 코드 |

## 3. 방법
- 데이터 변형(재개발 AI에게 주는 것)
  - V0 코드만(+원자료) / V1 서술형 문서(“이 시스템을 재구현할 수 있게 문서화하라” 1회 실행) /
    V2 구조화 명세(키트, 테스트 제외) / V3 구조화 명세 + 골든테스트(키트 전체) / V4 키트 + 코드 / V5 코드 + 키트 요약(동작 상세 제외)
- 생성 모델: Opus, 재개발 모델: Sonnet(데이터 차이가 더 잘 드러나도록), 각 변형 2회 반복
- 격리: 재개발 AI 작업폴더에는 해당 변형의 데이터만 둠. 전 세션의 도구 호출 경로를 감사(외부 경로 접근 0건 확인)
- 채점: 숨김 하네스(재개발 AI는 존재를 모름)로 블랙박스 비교. S2는 키트만 보는 답변자(Sonnet) + 별도 채점자(Opus)

## 4. 결과

### 4.1 S1 (작은 C FTL, 숨김 테스트 89개)
| 변형 | 점수(2회 평균) | 재개발 비용 | 시간 |
|---|---|---|---|
| V0 코드만 | 100% | $0.81 | 4.0분 |
| V1 서술형 문서 | 100% | $0.93 | 4.7분 |
| V2 구조화 명세(테스트 제외) | 100% | $1.55 | 7.5분 |
| V3 구조화 명세 + 골든테스트 | 100% | $1.04 | 4.2분 |
| V4 키트 + 코드 | 100% | $1.22 | 7.1분 |
생성 비용: 서술형 문서 $2.48(11분), 구조화 키트 $10.55(33분, 레거시 실행 기반 26개 골든 시나리오 포함).

→ 작고 깔끔한 코드는 **모든 형태가 천장(100%)**. 코드를 주면 AI는 거의 그대로 이식한다(변경 3~78줄).
  골든테스트가 있으면 같은 명세에서도 재개발이 빨라짐(V2 대비 비용 -33%).

### 4.2 S2 (실제 SSD 펌웨어, 재구현자 시험 70문항)
| 데이터 | 핵심사항 재현율 | 정답/부분/오답 | 생성 비용 | 크기 |
|---|---|---|---|---|
| 원본 코드(참고 상한선) | 87.3% | 36/33/1 | – | 81K tok |
| 서술형 문서 (2회) | 88.3% (89.2/87.4) | 39/31/0, 37/32/1 | $5.78 | 40K tok |
| 구조화 키트 Form X, 단일 세션 (2회) | 92.7% (92.2/93.1) | 48/22/0, 52/18/0 | $18.53 | 111K tok |
| 구조화 키트 Form Y, 파이프라인 — 종합 직후 (2회) | **95.1%** (94.8/95.4) | 54/16/0, 57/13/0 | $44.53 | 260K tok |
| 구조화 키트 Form Y — 검토·보완 후 | 94.1% | 56/14/0 | $107.3 | 895K tok (골든 데이터 포함, 명세 306K) |
| 최종 엔진 `max` 프리셋 (종합까지, 2회) | 94.8% (95.1/94.4) | 55/15/0, 54/16/0 | $44.92 | 296K tok |
| 최종 엔진 `balanced` 프리셋 (종합까지, 2회) | 94.4% (94.4/94.4) | 53/17/0 ×2 | $62.0* | 369K tok |

크기 = 텍스트 파일 바이트/3.6 추정(`kit_coverage.py`). 답변자는 필요한 파일만 골라 읽으므로 크기가 곧 답변 비용은 아니다.
결정적 커버리지(키트가 언급한 소스 함수/심볼 비율): 서술형 132/133(파일 20/34), Form X 113/133, Form Y **133/133(파일 34/34)** (최종 엔진 max·balanced도 133/133, 34/34).

→ 잘 만든 문서는 **원본 코드보다** 정확하고 싸게 답하게 한다(같은 문항 답변 비용 $2.2 vs $3.5).
  구조화 키트는 서술형보다 완전정답 +9~13문항, 파이프라인(Form Y)은 단일 세션(Form X)보다 정답 +2~6문항.
  모든 문서에서 오답(환각) 0~1. 반복 간 편차 약 ±1%p.
  검토·보완(코드 없는 구현자 AI가 빈틈 지적 → 코드 보는 AI가 보완)은 완전정답 수는 늘렸지만 재현율은 오르지 않았고
  비용은 2.4배 → `max` 프리셋에만 남김. 최종 엔진은 두 프리셋 모두 초기 실험(v1)과 같은 수준(94~95%)을 재현했다.
  \* balanced의 종합 세션이 스스로 서브에이전트 5개·백그라운드 작업을 띄워 $22(max는 $6)가 들었다 → 엔진 세션에서
  서브에이전트·백그라운드 도구를 금지하도록 수정(비용 예측 가능성).

### 4.3 S2 추가: 분석 단위 크기와 모델 (Form Y 엔진, 종합 단계까지)
| 설정 | 단위 수(평균 크기) | 핵심사항 재현율 | 정답/부분 | 비용 |
|---|---|---|---|---|
| Opus, 작은 단위 (v1) | 10개 (~8K tok) | **95.1%** (94.8/95.4) | 54~57/16~13 | $44.5 |
| Opus, 큰 단위 1개 (v2) | 1개 (81K tok) | 90.7% | 44/26 | $13.7 |
| Sonnet, 큰 단위 1개 (v2) | 1개 (81K tok) | 92.5% | 48/22 | $5.0 |
| Sonnet, 작은 단위 (v2) | 7개 (~12K tok) | 89.7% | 42/27 | $9.0 |
→ **Opus에서는 분석 단위를 작게(모듈 단위로 집중) 나눌수록 명세가 정밀**해진다(+4.4%p).
  큰 단위 하나로 몰아 읽으면 세부(계산식·경계값)가 빠진다. → 기본 단위 크기를 20K 토큰 이하로 결정.
  Sonnet은 작은 단위에서 오히려 낮았다(89.7% vs 92.5%, 1회씩) — 단위 간 통합에서 세부가 빠짐. → `economy`(Sonnet)는 큰 단위(40K).

### 4.4 S3 (Spring 배치, 숨김 체크 145개 = 코드로 알 수 있는 104 + 운영 지식 의존 41)
| 변형 | 점수 | 코드 도출 가능 체크 | 운영지식 의존 체크 | 재개발 비용 | 시간 |
|---|---|---|---|---|---|
| V0 코드만 (2회) | 134/145 (92.4%) | 104/104 | 30/41 | $3.19~3.91 | 24~30분 |
| V1 서술형 문서 (2회) | 134/145 (92.4%) | 104/104 | 30/41 | $1.85~2.09 | 11~17분 |
| V3 키트 Form X (2회) | 131, 134/145 | 101, 104/104 | 30/41 | $2.26~2.63 | 17~20분 |
| V4 키트 Form X + 코드 (2회) | 134/145 | 104/104 | 30/41 | $3.56~4.83 | 20~31분 |
| V3 키트 Form Y, 사람 없음 (2회) | 134/145 | 104/104 | 30/41 | $4.17~4.32 | 26~27분 |
| **V3 키트 Form Y + 질의응답 (2회)** | **145/145** | 104/104 | **41/41** | $4.98~6.20 | 37~40분 |
| **V4 키트 Form Y + 질의응답 + 코드 (2회)** | **145/145** | 104/104 | **41/41** | $5.77~6.24 | 33분 |
| **V5 코드 + 키트 요약(동작 상세 제외, 2회)** | **145/145** | 104/104 | **41/41** | $4.60~4.95 | 24~31분 |
- 코드나 문서만 있으면 **코드에 담긴 동작은 전부 재현**(MS949 바이트 처리, CSV 특이사항, 문서에 없는 E08, 반올림이 아닌 절삭, 06시 교대 경계 등).
  실패한 11개는 모두 **운영 서버에서만 설정되는 중복 정책(`-Dtlog.dup.policy=LAST`)** — 코드 기본값은 FIRST라 코드·문서로는 알 수 없다.
- 문서 기반 재개발은 코드 기반보다 **비용 약 45%↓, 시간 약 50%↓**(같은 점수).
- 질의응답 루프(모의 운영 담당자): 사전 인터뷰에서 운영 JVM 옵션·제외 범위·유지 계약을 확보하고, 1차 게이트에서 질문 11개
  (설계서 '재시험 5회' vs 코드 3회, 하드코딩된 OVR_E 판정, 정의서에 없는 E08, 경보 표본 기준 등)를 물어 답을
  `08_decisions.md`의 결정 25건으로 반영. 모르는 질문에는 "모르겠습니다"로 답하고 키트는 가정·위험으로 표시.
  코드만 보는 조사 단계도 **운영 시간대·중복 정책을 최우선 질문으로 스스로 식별**했다(사람 없는 실행).
