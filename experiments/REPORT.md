# 실험 보고서 — AI 재개발용 데이터의 형태와 생성 도구의 형태 결정

> 원자료: `experiments/results/` (`aggregate.py`로 재생성)

## 1. 실험 질문
| ID | 질문 |
|---|---|
| Q1 | AI가 레거시를 재개발하기에 **가장 효율적이고 충분한 데이터 형태**는 무엇인가? (코드 그대로 / 서술형 문서 / 구조화 명세 / 명세+골든테스트 / 명세+코드) |
| Q2 | 그 데이터를 만드는 **도구의 형태**: 단일 AI 세션(Form X) vs 결정적 오케스트레이션 파이프라인(Form Y) |
| Q3 | 코드만으로 알 수 없는 지식(운영 설정, 의도된 특이동작 등)을 **사람에게 묻는 루프**가 재개발 결과를 개선하는가? |

## 2. 실험 대상(샘플)
| ID | 종류 | 규모 | 실행/평가 방식 | 특징 |
|---|---|---|---|---|
| S1 | 실제 NAND 플래시 변환 계층(FTL) C 라이브러리(오픈소스 dhara를 비식별화) | C 3.2K LOC | 숨김 블랙박스 테스트 89개: 공개 API, 용량 계산, 전원 차단 33지점 트레이스, **온플래시 포맷 상호호환(구↔신)** | 작고 깔끔함, 모델이 원본을 학습했을 가능성 |
| S2 | 실제 NVMe SSD 펌웨어(Cosmos+ OpenSSD GreedyFTL 3.0) + PDF 자료 2종(198쪽) | C 8.8K LOC | 하드웨어 의존(실행 불가) → **재구현자 관점 시험 70문항(248 핵심사항)**, 코드 근거 정답 | 실제 펌웨어의 놀라운 동작(미기록 LBA 읽기 시 stale 데이터, FLUSH 무동작 등) 포함 |

| S4 | 합성 레거시 SSD 컨트롤러 펌웨어(NVMe 유사 명령, 쓰기 캐시, FTL, GC/WL, 배드블록, 리드리트라이, SMART, 전원断 복구) | C 수천 LOC | 숨김 테스트(명령 의미·SMART 값·온NAND 호환·전원断 등) | **릴리스 빌드 플래그**(운영 전용), 유지해야 할 버그성 동작, 미공개 코드 |

## 3. 방법
- 데이터 변형(재개발 AI에게 주는 것)
  - V0 코드만(+원자료) / V1 서술형 문서(“이 시스템을 재구현할 수 있게 문서화하라” 1회 실행) /
    V2 구조화 명세(키트, 테스트 제외) / V3 구조화 명세 + 골든테스트(키트 전체) / V4 키트 + 코드 / V5 코드 + 키트 요약(동작 상세 제외)
- 생성 모델: Opus, 재개발 모델: Sonnet(데이터 차이가 더 잘 드러나도록), 각 변형 2회 반복
- 격리: 재개발 AI 작업폴더에는 해당 변형의 데이터만 둠. 전 세션의 도구 호출 경로를 감사(외부 경로 접근 0건 확인)
- 채점: 숨김 하네스(재개발 AI는 존재를 모름)로 블랙박스 비교. S2는 키트만 보는 답변자(Sonnet) + 별도 채점자(Opus)

### 4.1 S1 (작은 C FTL, 숨김 테스트 89개)

|---|---|---|---|
| V0 코드만 | 100% | $0.81 | 4.0분 |
| V1 서술형 문서 | 100% | $0.93 | 4.7분 |
| V2 구조화 명세(테스트 제외) | 100% | $1.55 | 7.5분 |
| V3 구조화 명세 + 골든테스트 | 100% | $1.04 | 4.2분 |
| V4 키트 + 코드 | 100% | $1.22 | 7.1분 |
생성 비용: 서술형 문서 $2.48(11분), 구조화 키트 $10.55(33분, 레거시 실행 기반 26개 골든 시나리오 포함).

→ 작고 깔끔한 코드는 **모든 형태가 천장(100%)**. 코드를 주면 AI는 거의 그대로 이식한다(변경 3~78줄).
  골든테스트가 있으면 같은 명세에서도 재개발이 빨라짐(V2 대비 비용 -33%).

결정적 커버리지(키트가 언급한 소스 함수/심볼 비율): 서술형 132/133(파일 20/34), Form X 113/133, Form Y **133/133(파일 34/34)** (최종 엔진 max·balanced도 133/133, 34/34).

→ 잘 만든 문서는 **원본 코드보다** 정확하고 싸게 답하게 한다(같은 문항 답변 비용 $2.2 vs $3.5).
  구조화 키트는 서술형보다 완전정답 +9~13문항, 파이프라인(Form Y)은 단일 세션(Form X)보다 정답 +2~6문항.
  모든 문서에서 오답(환각) 0~1. 반복 간 편차 약 ±1%p.
  검토·보완(코드 없는 구현자 AI가 빈틈 지적 → 코드 보는 AI가 보완)은 완전정답 수는 늘렸지만 재현율은 오르지 않았고
  비용은 2.4배 → `max` 프리셋에만 남김. 최종 엔진은 두 프리셋 모두 초기 실험(v1)과 같은 수준(94~95%)을 재현했다.
  \* balanced의 종합 세션이 스스로 서브에이전트 5개·백그라운드 작업을 띄워 $22(max는 $6)가 들었다 → 엔진 세션에서
  서브에이전트·백그라운드 도구를 금지하도록 수정(비용 예측 가능성).

  큰 단위 하나로 몰아 읽으면 세부(계산식·경계값)가 빠진다. → 기본 단위 크기를 20K 토큰 이하로 결정.
  Sonnet은 작은 단위에서 오히려 낮았다(89.7% vs 92.5%, 1회씩) — 단위 간 통합에서 세부가 빠짐. → `economy`(Sonnet)는 큰 단위(40K).

- 실패의 대부분은 **릴리스 서버에만 있는 빌드 플래그**(`-DCFG_NAND_TYPE=TLC -DCFG_OP_PERCENT=12`; 저장소 기본값은 개발보드용
  QLC/7). 이 값 하나가 수명 계산·리드리트라이 표·용량·온NAND 슈퍼블록까지 바꿔 46개 체크를 좌우한다.
- 코드만 받은 AI는 운에 따라 결과가 갈렸다: 1회차는 주석의 "DEV defaults"를 보고 TLC를 추정해 161점, 2회차는 기본값을
  그대로 써 132점. 서술형 문서는 두 번 모두 기본값을 사실로 기록해 132점. → **추정이 맞을지 여부는 데이터로 통제할 수 없다.**
- 코드에 들어 있는 함정(문서·주석과 다르게 빅엔디언인 벤더 명령, 스펙과 다른 SMART 절삭, 유지해야 할 버그성 동작)은
  모든 변형이 코드대로 재현했다(코드 도출 가능 체크 전부 통과).
- 사람 없이 만든 키트도 조사 단계에서 **릴리스 빌드 플래그를 스스로 질문으로 올렸지만**, 답이 없으니 개발 기본값을 가정으로
  적용해 132점에 머물렀다. 질의응답 키트는 운영 담당자(모의)의 답(TLC/OP12, 릴리스 Makefile 제공)을 결정(DEC)으로 반영해
  **6회 모두 만점**. 키트+코드(V4)·코드+키트 요약(V5)은 AI가 레거시를 이식하고 결정 사항만 적용해 비용·시간이 가장 적었다.
- 키트 생성 비용: 사람 없음 $108.8, 질의응답 $167.3(사용량 한도로 중단된 검토 세션 재실행분 포함; 검토/보완 제외 시 $85).

### 4.6 종단간(E2E): 실제 사용 흐름 그대로 (S3, 최종 엔진, `balanced`, 사람 응답은 질문지 파일)
1. `rekit init` + 사전 인터뷰 없음(`--no-intake`) → `rekit run --bg` → 1차 게이트에서 **종료코드 10**(사람 확인 필요)으로 정지.
2. `rekit questions --export 질문지.md` → 운영 담당자 역할로 작성(24문항 중 20 답변, 4 "모름", 운영 샘플·기준정보 파일 경로 기재)
   → `rekit answer --import` (파일 경로는 자동으로 자료함에 복사되어 다음 단계에서 분석됨) → `rekit run` 재개.
3. 2차 게이트(검토 후 새 질문 24개, 필수 6개)에서 다시 정지 → 같은 방식으로 답변(아는 것만, 나머지 "모름" → 가정·위험으로 기록) → 완료.
- 결과 키트: 결정 35건(DEC), 테스트 벡터 299개 + 레거시 실행 골든 테스트, 남은 가정 13건·미해결 2건(경미), 소스 파일 56/56 언급.
  비용 $70.92(검토/보완 $26.9 포함), 약 3.5시간(사람 응답 대기 제외).

## 5. 결론과 설계 결정
| 질문 | 결론 | 근거 |
|---|---|---|
| Q1 데이터 형태 | **구조화 명세(계약/규칙/알고리즘/상태기계/오류) + 레거시 실행 골든 테스트 + 사람 확인 결정(DEC) + 열린 질문(가정)** 을 ID·출처·신뢰도로 연결한 "재개발 키트". 레거시 코드는 함께 주면 좋지만 필수는 아님 | S2 키트 95% > 코드 87%; S3·S4에서 키트만으로 만점(코드 함께 줘도 동일); 골든 테스트가 재개발 비용을 낮춤(S1 -33%) |
| Q2 도구 형태 | **결정적 오케스트레이션 파이프라인**(모듈 단위 병렬 분석 → 통합 → 사람 게이트 → 레거시 실행 특성화 → 마감), 재개 가능, Claude Code 플러그인 + CLI | 단일 세션보다 +2~4%p, 소스 커버리지 100%(단일 세션 85%); 장시간·대규모에서도 중단 후 재개 |
| Q3 사람 질의응답 | **필수.** 코드로 알 수 없는 운영 지식이 남은 실패의 전부였고, 질의응답 키트만 이를 해소 | S3 134→145, S4 132(161)→178; AI가 스스로 핵심 질문(운영 시간대·중복정책·빌드 플래그)을 찾아냄 |

설계 결정(실측 근거):
- **분석 단위는 작게**(모듈 단위, 기본 ≈20K 토큰 이하): 같은 Opus에서 95.1% vs 90.7%.
- **검토/보완 단계는 `max`에만**: S2에서 정답률 향상 없음(94.1% vs 95.1%), 비용 2.4배. 특성화(레거시 실행)는 항상.
- **사전 인터뷰에 "운영에서만 적용되는 설정 값/파일" 질문을 고정 포함**: 두 샘플 모두 가장 큰 실패 원인.
- **모르는 답은 가정으로 진행하고 위험으로 표시**(`09_open_questions.md`): 사람이 "모름"이라 해도 작업이 멈추지 않는다.
- **질문지(Markdown) 내보내기/가져오기**: 답변자가 코드·도구를 몰라도 되며, 답에 적은 파일 경로는 자동으로 자료로 편입.
- **엔진 세션은 서브에이전트·백그라운드 작업 금지**: 같은 단계 비용이 3.5배까지 흔들리는 것을 방지.
- 키트 언어는 한국어, 식별자·포맷·SQL·메시지는 원문 그대로(답변·재개발 모두 문제 없음).
