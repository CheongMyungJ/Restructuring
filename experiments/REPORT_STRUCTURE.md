# 실험 2 보고서 — 동작은 유지하고 레거시 구조 종속은 끊는 키트 (rekit 키트 형식 v3)

> 원자료: [`results/exp2_raw.md`](results/exp2_raw.md) · [`results/exp2_raw.json`](results/exp2_raw.json)
> (`exp2_structure.py`로 재생성). 이전 실험(데이터 형태·도구 형태 결정)은 [`REPORT.md`](REPORT.md).

## 1. 문제 제기와 가설
이전 키트(이하 **F2**)는 동작 재현에서는 만점을 받았습니다. 그런데 구조가 레거시를 그대로 따라가게 만드는 경로가 셋 있었습니다.
1. **레거시 모듈 단위로 정리된 명세.** `05_behavior/<레거시 모듈>.md`, `BR-<모듈>-NNN` ID, 그 단위를 따라가는 구현 계획이
   새 시스템의 모듈 경계를 미리 정해 버린다.
2. **"레거시에 충실한 의사코드".** 알고리즘이 루프 범위·호출 순서·헬퍼 단위까지 옮겨져 있어, 구현 AI는 다시 설계하지 않고
   언어만 바꿔 옮긴다. 명세 본문에 레거시 함수·변수 이름과 `(src: 파일:줄)`이 수백 번 등장한다.
3. **목표 설계 단계의 부재.** `02_architecture.md`는 "레거시 → 신규 매핑"일 뿐, 요구사항과 목표 스택에서 출발한 설계가 없다.
   README는 레거시 코드를 함께 두라고 권했다.

이전 보고서의 "키트 + 코드(V4)는 레거시를 이식하고 결정만 반영해 가장 빠르고 쌌다(S4 7분, $2)"는 관찰도 같은 문제였습니다.
비용·시간 면에서는 장점이었지만, 결과물은 사실상 이식(port)이었습니다.

가설: **무엇을(명세)**, **새로 어떻게(목표 설계)**, **레거시는 어떻게(참고)** 를 분리한 키트는 숨김 테스트 점수를 그대로
유지하면서 재개발 결과의 레거시 구조 유사도를 크게 낮춘다.

## 2. 무엇을 바꿨나 (키트 형식 v3, 이하 F3)
| 영역 | F2 (이전) | F3 (현재) |
|---|---|---|
| 층 구조 | 하나의 명세에 '무엇'과 '어떻게'가 섞임 | **명세(spec)** / **목표 설계(design/)** / **레거시 참고(legacy_ref/)** 3층 |
| 동작 명세 단위 | 레거시 모듈별 `05_behavior/<모듈>.md` | 외부 관점의 **기능(capability)별** `05_behavior/CAP-*.md` |
| 알고리즘 | 레거시에 충실한 의사코드(전부) | 관측 결과를 **결정할 때만**, 선언적(기준·동률 처리·공식·`결과 결정: …`). 제어 흐름 의사코드는 legacy_ref |
| 이름·출처 | 레거시 함수·변수·파일 이름과 `(src:)`가 본문에 | 명세·설계에 **레거시 내부 이름·파일명·소스 경로 금지**(계약 식별자만 원문). 출처는 `trace.json`에만 |
| 목표 설계 | 없음(레거시→신규 매핑) | **클린룸 설계 단계**: 레거시 코드 접근 없이(작업 폴더 격리, 파일 도구만) 명세·사전 인터뷰·구조 문제 목록으로 구성요소 C-*, ADR, 할당표 작성 |
| 레거시 구조 문제 | 기록 없음 | 분석 단계에서 구조 문제(LP-*) 수집 → 설계 ADR이 하나씩 회피 |
| 계약 경계 | — | **계약 경계 점검 단계**: 다른 쪽이 구현·호출하는 경계(호스트 API, HAL, 스크립트, DDL)는 정확한 형태 유지, 경계 파일 원문 동봉 |
| 누출 검사 | — | **결정적 누출 검사**(명세·설계에 남은 레거시 내부 이름·파일명·소스 경로) + AI 보정 |
| 구현 계획 | 레거시 단위 순서 | 목표 설계 구성요소 순서, 컨텍스트 팩에 legacy_ref 제외 |
| 구현 규칙 | "레거시 코드도 함께 두면 더 정확" | 구조는 design/, 동작은 명세. 레거시는 특정 ID 모호점만, **작업 공간에 두지 않음**. 구조 자가 점검 도구 동봉 |

파이프라인: `inventory → survey(기능 목록) → units(두 관점 기록) → synthesize → specify(기능별) → gate1 → characterize →
[review] → contracts → gate2 → neutralize → design(클린룸) → finalize`.

## 3. 평가 지표 — 레거시 구조 유사도(LSS)
숨김 테스트는 동작만 봅니다. 구조가 얼마나 레거시를 닮았는지는 새 결정적 지표로 측정했습니다(`rekit similarity`, 표준 라이브러리만,
C/C++/Java/Kotlin/JS/TS/Python).

| 지표 | 정의 | 무엇을 잡나 |
|---|---|---|
| M1 파일 대응률 | 레거시 소스 파일 중, 같은 정규화 파일명이 신규에 있거나 그 파일 비자명 함수의 절반 이상이 **한** 신규 파일로 대응하는 비율 | 모듈 경계 보존 |
| M2 내부 이름 재사용 | 레거시가 정의한 내부 이름(함수·타입·클래스·매크로, 4자 이상, 계약 식별자 제외) 중 신규가 다시 정의한 비율 | 이름 이식 |
| M3 구조 클론률 | 신규 코드의 토큰 20-gram 중, 식별자·리터럴을 지운 뒤 레거시에도 있는 비율 (원문 그대로 비율 별도) | 복사 + 이름 바꾸기 |
| M4 함수 대응률 | 레거시 비자명 함수(정규화 토큰 40개 이상) 중 정규화 5-gram Jaccard ≥ 0.5인 신규 함수가 있는 비율 | 함수 분해·본문 형태 보존 |
| **LSS** | 100 × 평균(M1~M4) | 0 = 독립, 100 = 레거시 그 자체 |

- **보정(calibration)**
  - 레거시 자기 자신 = 100.0
  - 이름만 전부 바꾼 복사본: M2 = 0인데도 M3 ≥ 0.9, M4 = 1.0으로 이식으로 판정됨(단위 테스트)
  - 같은 저자가 별도로 쓴 하네스 시뮬레이터: 3.5
  - 서로 무관한 두 샘플: 0.0
- **계약 파일**: 재개발 과제가 그대로 유지하라고 요구한 파일(S4의 `fw_api.h`, `hal/*.h`)은 양쪽에서 제외하고, 그 식별자는 재사용으로 세지 않음. 모든 변형에 같은 목록을 적용함.
- **S4 core**: 시뮬레이터·CLI·ASIC BSP를 빼고 펌웨어 본체만 비교한 값. 숨김 하네스가 링크하는 범위와 같음.

키트에는 명세 층의 **구조 누출**(`rekit.neutrality`)도 결정적으로 셉니다. 대상은 레거시 내부 이름(코드 형태 식별자), 레거시 소스 파일명, 소스 경로 표기이며, 계약 문서(03·04)에 나오는 이름과 언어·빌드 공통 이름은 제외합니다.

## 4. 방법
- 샘플: S3(Java/Spring 배치, 숨김 체크 145)와 S4(C SSD 펌웨어, 숨김 체크 178). 둘 다 운영 지식 함정과 숨김 블랙박스 하네스가 있음.
- 키트 생성
  - 설정: Opus, `balanced`, 모의 담당자 질의응답(oracle)
  - F2: 이전 엔진(실험 시작 시점 커밋 `8181d40` 고정)
  - F3: 새 엔진
  - 목표 스택은 재개발을 의뢰하는 쪽이 아는 정보이므로, F3 사전 인터뷰의 '목표 스택' 답에 재개발 과제와 같은 스택을 넣음. 모의 담당자의 원래 답은 "모르겠습니다"였음(§6).
- 재개발
  - 설정: Sonnet, 같은 과제 프롬프트(이전 실험과 동일), 각 2회, 작업 폴더에는 해당 데이터만 둠(외부 경로 접근 감사 0건)
  - V0: 코드만
  - V3: 키트만
  - V4: 키트 + 레거시 코드
- 반복 개선: F3.0 → F3.1 → F3.2. 각 단계는 앞 단계 결과에서 드러난 실패를 고친 것(§5.3). 같은 분석 결과(units~characterize)를 재사용하고, 바뀐 단계 이후만 다시 실행함.

남은 유사도:
- 대부분 외부 사양이 정한 이름입니다. 레거시 구조와는 무관합니다.
  - 하드웨어 레지스터·비트 이름(`CC_SHN_*`, `I2C_*`, `ECC_RES_*`)
  - 빌드 플래그와 식별 정보 상수(`CFG_NAND_TYPE`, `FW_IEEE_OUI`)
  - 누가 짜도 비슷한 작은 유틸리티(CRC, 엔디안 변환)

## 7. 한계
- 샘플 2종, 변형별 2회. 같은 조건에서도 구조 유사도의 편차가 컸다. 특히 레거시 코드를 함께 준 V4에서 컸다(S4 F3.1: 24.3 / 51.4).
- LSS는 토큰·이름·함수 경계 기반의 정적 지표로, 설계 품질 자체(응집도, 테스트 용이성)를 측정하지는 않는다. 두 경우는 상한·하한을 정해 놓은 단위 테스트로 검증했다.
  - 이름을 바꾼 이식은 높게 나와야 한다.
  - 독립 설계는 낮게 나와야 한다.
- CRC·엔디안 변환처럼 누가 짜도 비슷한 작은 함수는 M4에 일부 남는다. 설정 매크로 이름 같은 도메인 상수 이름도 M2에 일부 남는다.
- 목표 스택은 사전 인터뷰에 넣었다. 모의 담당자가 "모르겠습니다"라고 답한 그대로 두면, 클린룸 설계가 과제와 다른 스택(배치 프레임워크 없는 Java)을 골랐다(S3 1차 설계). 실제 사용에서는 사전 인터뷰에서 목표 스택을 꼭 받아야 한다.
- F3.1과 F3.2는 F3.0의 분석 결과를 재사용해 일부 단계만 다시 돌렸다. 처음부터 끝까지 한 번에 새로 생성한 F3.2 키트는 측정하지 않았다.
- 재개발 모델은 Sonnet, 생성 모델은 Opus. 비용은 Claude Code 보고값(`total_cost_usd`) 기준이다.
